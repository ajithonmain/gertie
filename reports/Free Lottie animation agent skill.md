# Compile, Validate, Render: A Free Lottie Skill

A free, open alternative to Lottie AI is buildable today from permissively licensed parts, provided the skill never asks the model to hand-write Lottie JSON. The model should instead write a compact timeline spec or builder script that a small bundled compiler turns into Lottie JSON, which is then checked against the official schema, linted, and rendered to frames the agent inspects. This matters because single-shot raw JSON from general LLMs succeeded only about 9 to 13% of the time in the one published benchmark, and because LottieFiles' own paid product reportedly uses the same compile-and-repair pattern rather than raw emission. The paid offering is real: LottieFiles launched Lottie AI in the week of 12 November 2026, and its cheapest paid plan is $19.99 per user per month billed annually with 60 generations, while its own policy page bars commercial use below the $24.99 Team tier. Animated SVG is best emitted directly from the same timeline spec as SMIL or in-file CSS keyframes, because the free Lottie-to-SVG converters are thin, SMIL-only and copyleft or stale. Video, GIF and every transparent format come from one pipeline: a headless renderer writes RGBA PNG frames and ffmpeg encodes them, with recipes for transparent GIF, APNG, WebP, VP9-alpha WebM, ProRes 4444 and HEVC-alpha already verified locally on ffmpeg 7.1.1. The field is not empty (a 5,700-star MIT skill already does text-to-Lottie), so the differentiators are validation, a render loop, SVG output and transparent exports. The main licence traps are AGPL and GPL tools (python-lottie, gifski, Glaxnimate), Remotion's company licence, and LottieFiles product names.

## Lottie AI charges $19.99 a month and withholds commercial rights below Team

LottieFiles launched a standalone text-to-Lottie product, **Lottie AI**, on Product Hunt with a leaderboard date of 12 November 2026 and the tagline "Editable vector animations from a text prompt" ([Product Hunt](https://www.producthunt.com/products/lottiefiles?launch=lottie-ai)). The "roughly 20 dollars" figure maps to the Individual plan at **$19.99 per user per month, billed annually**, which includes a 300-credit monthly pool and caps Lottie AI at **60 generations per month**; Team costs $24.99 per user with a two-editor minimum and 120 generations, and top-ups cost 20 cents per credit ([LottieFiles pricing](https://lottiefiles.com/pricing)). A free Starter tier exists with "free generations", 5 file uploads and 20 MB of storage ([Lottie AI pricing](https://lottie.ai/pricing)). Two things remain unverified: the paid prices shown on lottie.ai itself (rendered by JavaScript and unreadable to the researchers) and any month-to-month price, since only annual billing is displayed.

The more consequential finding is a licensing contradiction. The Lottie AI landing page says everything generated "comes with a full commercial AI license" ([Lottie AI](https://lottie.ai/)), yet the LottieFiles commercial-use guide, updated 10 November 2026, states that commercial use is **not allowed on Starter or Individual** and begins at Team, and that this "applies to work you create, edit, or customize using LottieFiles services" ([LottieFiles commercial use guide](https://help.lottiefiles.com/commercial-use-guide)). Until LottieFiles reconciles the two pages, a freelancer on the $19.99 plan cannot be sure of commercial rights. A free MIT-licensed skill whose output carries no such restriction has a clear, defensible advantage here, larger than the price difference itself.

Technically, Lottie AI takes a prompt plus optional duration, canvas size, palette and imported SVG, image or Lottie JSON, and returns named, grouped vector layers with a per-animation control panel for colour, size, timing and text; it offers a single-pass Turbo mode and a multi-agent plan-and-critique Quality mode, and exports dotLottie, Lottie JSON, GIF, MP4, WebM, MOV and SwiftUI or Jetpack Compose code ([Lottie AI](https://lottie.ai/)). Its makers state that "it writes a small animation language that our compiler turns into clean, lightweight Lottie" and that "the AI repairs its own code before you ever see it" ([Product Hunt](https://www.producthunt.com/products/lottiefiles?launch=lottie-ai)). These are vendor statements, and no independent benchmark or community review existed one day after launch, but the design signal is clear: the company with the most Lottie expertise chose an intermediate language, a compiler and a repair loop over direct JSON emission. LottieFiles also concedes that "AI can be unpredictable generating illustration shapes from scratch" and recommends importing your own SVGs first ([LottieFiles blog](https://lottiefiles.com/blog/working-with-lottie-animations/your-ai-can-now-control-lottie-creator-heres-what-that-actually-means)).

The surrounding market meters AI by credits. Rive bundles $20 to $40 of AI credits per seat on its upper tiers but lets users build with the Rive CLI from their own coding agent for free ([Rive pricing](https://rive.app/pricing)); SVGator, Jitter and LottieLab are reported at roughly $12 to $35 per editor per month, though those figures come from secondary sites and were not confirmed on vendor pages ([yespress SVGator](https://yespress.io/svgator), [toolradar LottieLab](https://toolradar.com/tools/lottie-lab/pricing)). A skill that runs on the user's existing LLM subscription has no per-generation fee at all.

## Lottie is a small JSON scene graph with a machine-checkable safe subset

A Lottie file is a JSON scene graph. The root animation carries width `w`, height `h`, frame rate `fr`, in and out points `ip` and `op`, and a `layers` array; each layer has a type `ty` (0 precomposition, 1 solid, 2 image, 3 null, 4 shape), an index `ind` used for parenting, and a transform `ks` ([Lottie spec: layers](https://lottie.github.io/lottie-spec/latest/specs/layers/)). Shape layers hold a `shapes` array of geometry (`rc` rectangle, `el` ellipse, `sh` bezier path, `sr` polystar), styles (`fl` fill, `st` stroke, `gf` and `gs` gradients), the `tm` trim-path modifier, and `gr` groups that end with a `tr` transform ([Lottie spec: shapes](https://lottie.github.io/lottie-spec/latest/specs/shapes/)). Every animatable value is a property `{a, k}`: `a` is 0 with a static value in `k`, or 1 with `k` holding keyframes that each carry a frame number `t`, a value `s`, and cubic-bezier easing handles `o` and `i` on a curve from [0,0] to [1,1] ([Lottie spec: properties](https://lottie.github.io/lottie-spec/latest/specs/properties/)). Because `o` is the first control point and `i` the second, a CSS `cubic-bezier(x1, y1, x2, y2)` maps directly to `o = {x: x1, y: y1}`, `i = {x: x2, y: y2}`, which lets a skill offer named easing presets instead of raw numbers.

The format's rules are what trip models up, and the spec states them explicitly. Shapes render in reverse array order, styles apply to the shapes that precede them in the same scope, a transform must be present in every group and must be last, and **geometry with no applicable style is simply not rendered**; keyframe times must ascend, and `i` and `o` are required on every keyframe except the last or a hold ([Lottie spec: shapes](https://lottie.github.io/lottie-spec/latest/specs/shapes/), [properties](https://lottie.github.io/lottie-spec/latest/specs/properties/)). Each of these is mechanically enforceable, which is the whole argument for a compiler.

The authoritative standard is the Lottie Animation Community specification, a Linux Foundation project, currently **version 1.0.1**, published with a JSON Schema in draft 2020-12 ([Lottie spec schema](https://lottie.github.io/lottie-spec/latest/specs/schema/), [lottie.github.io](https://lottie.github.io/)). That spec deliberately covers a conservative core, and this core lines up closely with what every player supports. Airbnb's cross-platform table shows that shapes, groups, solid and gradient fills and strokes, transforms with parenting, linear, bezier and hold keyframes, precomps, add and subtract masks, and alpha mattes work on Android, both iOS engines, Windows and all three web renderers, whereas **expressions are web-only, merge paths fail on iOS and web, luma mattes fail on Android, iOS and Windows, auto-orient is web-only, and layer effects and text are patchy** ([airbnb/lottie supported features](https://raw.githubusercontent.com/airbnb/lottie/master/supported-features.md)). ThorVG, the engine behind the MIT-licensed dotLottie players, supports far more, including most effects and partial expressions ([ThorVG wiki](https://github.com/thorvg/thorvg/wiki/Lottie-Support)), but a portable skill should target the intersection. The practical rule that follows (an inference from these tables, not a published guarantee) is that a file which validates against the 1.0.1 schema with zero unknown-property warnings is very likely to play everywhere.

dotLottie (`.lottie`) is an optional packaging step, not a different animation format: it is a Deflate ZIP with a root `manifest.json` and animations under `a/`, plus optional images, fonts, themes and state machines, with themes targeting Lottie slot IDs ([dotLottie 2.0 spec](https://dotlottie.io/spec/2.0/)). Because it is an ordinary ZIP, a skill can produce it with a standard zip library and no extra dependency; theming and state machines, however, only work in dotLottie players, so plain JSON stays the baseline output.

## Raw JSON fails nine times in ten; a compiler and three gates fix it

The only quantitative evidence on LLM Lottie authoring comes from OmniLottie (CVPR 2026). In its text-to-Lottie benchmark, **GPT-5 reached a 12.7% success rate, DeepSeek 9.3% and Qwen2.5-VL 0%**, against 88.3% for the fine-tuned OmniLottie model ([arXiv 2603.02138](https://arxiv.org/html/2603.02138v1)). The paper's appendix and supplement report different figures for some rows (for example 97.3% for OmniLottie on text), an internal inconsistency, so the precise numbers deserve caution while the order-of-magnitude gap does not. The failure modes are instructive: schema hallucination such as `"version": "2.0"` in place of `v`, colour attributes placed on geometry rather than in separate fill nodes, and, for GPT-5 and Gemini, **schema-valid JSON that still renders wrongly** because of collapsed bezier control points, incorrect transform nesting and non-monotonic keyframe times ([arXiv 2603.02138](https://arxiv.org/html/2603.02138v1)). The fix in that paper was representational: replacing raw JSON (about 2,562 tokens per animation) with a compact command sequence (about 486 tokens), a 5.3-fold reduction. A second CVPR 2026 paper, LottieGPT, takes the same tokenised route ([arXiv 2604.11792](https://arxiv.org/abs/2604.11792)).

Those benchmarks measure one-shot generation with no tools, so they are a floor for a tool-using agent, not a ceiling; no study yet measures an agent with a builder, a validator and render feedback, and none compares raw JSON, builder scripts and SVG conversion head to head. The recommendation here is therefore reasoned rather than measured, but three independent lines point the same way: the research result, LottieFiles' own compiler architecture, and the fact that every listed failure mode is something a compiler can make unrepresentable. A builder always appends the group transform, always pairs `a` with the right shape of `k`, sorts keyframes, fills easing handles from presets, converts hex colours to 0-to-1 floats, assigns layer indices and sets `ip` and `op` from the composition.

No existing library fills this role cleanly. python-lottie is the most capable builder and converter but is **AGPLv3+** with its last release (0.7.2) in May 2025 ([PyPI](https://pypi.org/pypi/lottie/json)); `@lottiefiles/lottie-js` is MIT but has not been published since July 2023 ([npm](https://registry.npmjs.org/@lottiefiles/lottie-js)); relottie is an MIT abstract-syntax-tree toolchain suited to post-processing rather than authoring ([relottie](https://github.com/LottieFiles/relottie)). Since the safe subset amounts to about ten shape item types, one transform object and one keyframe shape, a purpose-written, dependency-free compiler of a few hundred lines is the realistic and licence-clean choice. The specialised open models are not a zero-cost answer for most users: OmniLottie's code is Apache-2.0 but the 4-billion-parameter model needs about 15.2 GB of GPU memory, and its training dataset is non-commercial ([OmniLottie](https://github.com/OpenVGLab/OmniLottie)).

Schema validity is necessary but not sufficient, so the skill needs three gates. The first is schema validation with the MIT `@lottie-animation-community/lottie-specs` package, whose `LottieValidator` returns schema errors plus warnings for unknown object types and unknown properties ([lottie-specs-js](https://github.com/lottie/lottie-specs-js)); treating those warnings as errors catches hallucinated keys and out-of-subset features in one pass, and any draft 2020-12 validator works against the published schema if Node is unavailable. The second is a semantic lint the skill must supply itself, since no maintained open linter was found: keyframe order, easing `x` within 0 to 1, reference integrity for `parent` and `refId`, a style in scope for every geometry, transform last in each group, value ranges (colours 0 to 1, opacity and scale 0 to 100), and layer `ip`/`op` coverage. The third is an actual render of sample frames, which a vision-capable agent reviews as a contact sheet and a text-only agent checks numerically (frames non-empty, frames differ from one another). For artwork, the best-supported practice is to ground the animation in concrete assets: the leading open skill reports "significantly better" results when starting from SVGs ([diffusionstudio/lottie](https://github.com/diffusionstudio/lottie)), and LottieFiles gives the same advice.

## Animated SVG works in an img tag only as SMIL or in-file CSS

An SVG can animate three ways, and only two survive where images are used. MDN states that when SVG is used as an image, JavaScript is disabled and external resources cannot load, with those restrictions lifted only when the file is viewed directly or embedded through `iframe`, `object` or `embed` ([MDN: SVG as an image](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/SVG_as_an_image)). That rules out the obvious trick of inlining lottie-web inside an SVG: lottie-web's SVG renderer is a JavaScript runtime that rewrites the DOM each frame ([npm lottie-web](https://www.npmjs.com/package/lottie-web)), so such a file renders blank or static in `<img>`, CSS backgrounds and GitHub READMEs. The two mechanisms that do survive are **SMIL, which has 97.4% global support** and is not deprecated in any current browser ([caniuse SMIL](https://caniuse.com/svg-smil)), and CSS `@keyframes` inside the SVG's own `<style>` block, which is reported to play even in GitHub README images ([CSS-Tricks](https://css-tricks.com/custom-styles-in-github-readmes/)). One low-quality source claims in-file CSS does not run inside `<img>`; the weight of evidence says it does, but nobody in this research ran the five-minute browser test that would settle it, and the skill's test suite should. Email is a separate case where a GIF fallback remains the safe choice.

Converting Lottie to animated SVG with free tools is the weakest link in the whole stack. Only two open-source converters emit truly animated output, both SMIL: Glaxnimate (**GPLv3+**), whose Python module ships only a Linux x86-64 wheel with no macOS build ([PyPI glaxnimate](https://pypi.org/project/glaxnimate/)), and bodymovin-to-smil, a Node library with "basic" feature support that was last touched around 2022 ([bodymovin-to-smil](https://github.com/bodymovin/bodymovin-to-smil)). python-lottie's `--animated` SVG option does not generate SMIL itself; it delegates entirely to Glaxnimate ([python-lottie source](https://gitlab.com/mattbas/python-lottie/-/raw/master/lib/lottie/parsers/svg/builder.py)). The popular `lottie-to-svg` package renders one static frame ([npm lottie-to-svg](https://www.npmjs.com/package/lottie-to-svg)), LottieFiles' own SMIL export lives in GUI tools with no CLI ([LottieFiles docs](https://docs.lottiefiles.com/en/integrations/vscode/05_integrate/choosing-an-output-format.md)), and no open-source Lottie-to-CSS-keyframes converter was found. None of these converters was executed during the research, so their fidelity on trim paths, mattes and gradients is unknown.

The dependable answer is to stop converting. If the skill's source of truth is a neutral timeline spec, it can run two emitters, one producing Lottie JSON and one producing SVG with CSS keyframes and SMIL, and depend on no converter in either direction. This is an architectural inference rather than an existing tool, but it follows directly from the converter landscape, and SVG plus CSS is a format models already write well. The SVG emitter needs a handful of encoded rules. CSS `d` path morphing parses but has no effect in Safari, so **morphs must use SMIL `<animate attributeName="d">`** with identical command structure in every value ([MDN browser-compat-data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/css/properties/d.json)). `transform-box: fill-box` is supported from Chrome 64, Firefox 55 and Safari 11 and should accompany every rotating or scaling element ([MDN browser-compat-data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/css/properties/transform-box.json)). Trim paths map to `pathLength="1"` with animated `stroke-dashoffset`, everything must be self-contained in one file with no script or external assets, and a `prefers-reduced-motion` rule belongs in the style block; these last practices are standard technique that the researchers did not individually source, so they should be confirmed by rendering tests. Optimisation uses SVGO (MIT, v4.1.0), but its default preset includes plugins such as `cleanupIds`, `removeHiddenElems`, `convertPathData`, `mergePaths` and `collapseGroups` ([SVGO preset-default](https://svgo.dev/docs/preset-default/)) that are likely to break animation targets, so the skill should ship a conservative config with those disabled.

The honest boundary is that SVG cannot express everything Lottie can: runtime control, state machines, complex mattes and native mobile playback remain Lottie's territory, and animated SVG only runs in browser engines. The skill should present SVG as the zero-runtime deliverable for icons, loaders and illustrations, and Lottie as the deliverable for apps and richer motion.

## One PNG-frame pipeline feeds every raster target, transparency included

All video and image outputs should flow through a single path: a headless renderer writes RGBA PNG frames, then ffmpeg encodes. Three MIT-licensed renderers are current as of November 2026. The reference-fidelity option is lottie-web (5.13.0) driven by Playwright (1.65.0) or Puppeteer (25.17.0), seeking with `goToAndStop(frame, true)` and capturing with `omitBackground: true` ([npm lottie-web](https://registry.npmjs.org/lottie-web), [npm playwright](https://registry.npmjs.org/playwright)). The fast, browserless options are `@napi-rs/canvas` 1.1.1, which ships a Skia Skottie `LottieAnimation` class with `seekFrame` and `render` and claims zero system dependencies ([Brooooooklyn/canvas](https://github.com/Brooooooklyn/canvas)), and `@lottiefiles/dotlottie-web` 0.83.2, whose ThorVG core runs in Node ([npm dotlottie-web](https://registry.npmjs.org/@lottiefiles/dotlottie-web)). The researchers drafted but did not execute scripts for these, so they are designs to be tested, not proven code. What to avoid is clearer: `puppeteer-lottie` and its CLI are pinned to Puppeteer 2.x from 2020 ([npm puppeteer-lottie](https://registry.npmjs.org/puppeteer-lottie)), rlottie's README declares it deprecated and unmaintained ([Samsung/rlottie](https://github.com/Samsung/rlottie)), and Remotion requires a paid company licence beyond three people ([Remotion pricing](https://www.remotion.dev/docs/license/pricing)).

The same browser harness captures animated SVG and HTML deterministically. Real-time recorders are unsuitable: Playwright's `recordVideo` offers no frame-rate or codec control and scales to fit 800 by 800 ([Playwright docs](https://playwright.dev/docs/videos)), and the timecut family explicitly does not handle CSS animations and is also pinned to Puppeteer 2.x ([timecut](https://github.com/tungs/timecut)). The approach instead is to pause every clock and seek per frame, using `document.getAnimations()` with `currentTime` for CSS and Web Animations and `svg.pauseAnimations()` with `setCurrentTime()` for SMIL; these are standard web APIs that the researchers named from prior knowledge without fetching reference pages or running the script.

The encoding step is the best-verified part of this report. Every recipe below ran successfully on ffmpeg 7.1.1 on macOS arm64 against a 512 by 512, 30 fps, 90-frame RGBA sequence; behaviour on the current Homebrew ffmpeg 9.x was not rechecked.

```bash
# Transparent GIF (1-bit alpha)
ffmpeg -y -framerate 30 -i frames/f_%04d.png -filter_complex \
 "[0:v]fps=25,split[a][b];[a]palettegen=reserve_transparent=1:stats_mode=full[p];[b][p]paletteuse=dither=bayer:bayer_scale=5:alpha_threshold=128" \
 -gifflags -offsetting -loop 0 transparent.gif

# APNG (lossless, 8-bit alpha, infinite loop)
ffmpeg -y -framerate 30 -i frames/f_%04d.png -plays 0 -pred mixed out.apng

# Animated WebP with alpha (leave -compression_level at its default)
ffmpeg -y -framerate 30 -i frames/f_%04d.png -c:v libwebp_anim -lossless 0 -q:v 80 -loop 0 out.webp

# WebM VP9 with alpha (Chrome, Firefox, Edge, Telegram)
ffmpeg -y -framerate 30 -i frames/f_%04d.png -c:v libvpx-vp9 -pix_fmt yuva420p -b:v 0 -crf 30 -row-mt 1 -auto-alt-ref 0 -an alpha.webm

# ProRes 4444 with alpha (video editors)
ffmpeg -y -framerate 30 -i frames/f_%04d.png -c:v prores_ks -profile:v 4444 -pix_fmt yuva444p10le -alpha_bits 16 -vendor apl0 -an alpha.mov

# HEVC with alpha for Safari and iOS (macOS only)
ffmpeg -y -framerate 30 -i frames/f_%04d.png -c:v hevc_videotoolbox -allow_sw 1 -alpha_quality 0.75 -q:v 65 -tag:v hvc1 -pix_fmt bgra -an alpha_hevc.mov

# Opaque MP4 over a solid colour
ffmpeg -y -f lavfi -i "color=c=white:s=512x512:r=30" -framerate 30 -i frames/f_%04d.png \
 -filter_complex "[0:v][1:v]overlay=shortest=1,format=yuv420p" -c:v libx264 -crf 18 -preset slow -movflags +faststart -an solid.mp4
```

Three traps surfaced in that testing. Setting `-compression_level 6` on `libwebp_anim` ran for more than three minutes on 90 frames where the default finished in about a second. `ffprobe` reports VP9-alpha and HEVC-alpha files as `yuv420p`, so alpha must be verified another way (for VP9, by forcing the `libvpx-vp9` decoder and checking for an RGBA frame). And HEVC with alpha can only be encoded through Apple's VideoToolbox ([FFmpeg trac #7965](https://trac.ffmpeg.org/ticket/7965)), so a Linux agent cannot produce the Safari video asset and should fall back to APNG or animated WebP there.

Transparent GIF deserves its own warning in the skill. GIF supports only binary transparency ([ImageMagick forum](https://imagemagick.com/discourse-server/viewtopic.php?p=146825)), one palette entry is reserved for it leaving 255 colours, and anti-aliased edges become either jagged (thresholded) or haloed (pre-blended toward a matte colour that only looks right on one background). Frame delays are whole centiseconds, so exact rates are 50, 25, 20, 12.5 or 10 fps; a 30 fps Lottie should be resampled to 25. In the local test, ffmpeg set disposal method 2 on every transparent frame automatically, which prevents ghosting. gifski produces the best GIFs and has a `--matte` flag for the edge problem, but it is **AGPL-3.0** ([gifski](https://github.com/ImageOptim/gifski)), and gifsicle is GPL-2.0, so both should be optional external tools. The skill should steer users to a better format whenever the destination accepts one.

| Destination | First choice | Constraint or fallback |
|---|---|---|
| Web page, small icon in `<img>` | Animated WebP with alpha | APNG, then GIF |
| Web page, larger `<video>` | VP9-alpha WebM plus HEVC-alpha source for Safari | Opaque MP4 on a matching background |
| Telegram video sticker | WebM VP9, one side 512 px | 3 s, 30 fps, 256 KB maximum |
| Discord sticker | APNG, exactly 320 by 320 | 512 KB maximum |
| Slack emoji | Transparent GIF, square | Under 128 KB, 50 frames maximum |
| WhatsApp sticker | Animated WebP 512 by 512 | 500 KB (third-party sources) |
| Video editors | ProRes 4444 MOV | PNG sequence |
| Email | GIF | Static PNG |

Browser support underpins the first rows: APNG and WebP each sit above 97% global support ([caniuse APNG](https://caniuse.com/apng), [caniuse WebP](https://caniuse.com/webp)), VP9 alpha works in Chrome and Firefox but not Safari, which needs HEVC with alpha ([Jake Archibald](https://jakearchibald.com/2024/video-with-transparency/)). Platform limits come from [Telegram](https://core.telegram.org/stickers), [Discord](https://support.discord.com/hc/articles/4402687377815) and [Slack](https://slack.com/help/articles/206870177-Add-custom-emoji-and-aliases-to-your-workspace). Which transparent formats PowerPoint, Keynote and Google Slides accept could not be sourced. As a size guide, the synthetic gradient test produced 39.8 KB for VP9-alpha WebM, about 143 KB for transparent GIF, about 300 KB for animated WebP, 769 KB for APNG and 1,160 KB for ProRes 4444; flat-colour icons will be much smaller in the image formats, so these are upper-range indications from one test, not typical values.

## Existing free skills skip validation and export, and SKILL.md ports everywhere

The field already has a strong free entrant. `diffusionstudio/lottie`, an MIT-licensed text-to-lottie skill released on 8 June 2026, has about 5,700 stars; the agent writes Lottie JSON into a project folder that a bundled player live-reloads, and it suits short, single-scene animations ([diffusionstudio/lottie](https://github.com/diffusionstudio/lottie), [Diffusion Studio changelog](https://diffusion.studio/changelog/text-to-lottie)). Its README documents no automated validation, schema check or headless render loop, though its internal instruction files were not read, so that gap is inferred from public documentation. Around it sit `LottieFiles/motion-design-skill` (MIT, about 3,000 stars), a knowledge-only skill on timing, easing and choreography that is worth recommending alongside any generator ([motion-design-skill](https://github.com/LottieFiles/motion-design-skill)); `obeskay/lottie-animator-skill` (MIT, 24 stars), which animates from SVGs ([lottie-animator-skill](https://github.com/obeskay/lottie-animator-skill)); and several skill packs that only cover playing existing Lottie files. None of the open skills surveyed clearly advertises transparent WebM, MOV or GIF export, which LottieFiles lists among its plan features. A new skill should therefore not compete on "text to Lottie" alone; its distinct value is the compiler with validation gates, the dual Lottie and animated-SVG output, and the transparent export pipeline.

Packaging is the easiest part, because the Agent Skills format has become a genuine cross-vendor standard. A skill is a folder containing a `SKILL.md` with YAML frontmatter (`name`, at most 64 lowercase characters and matching the directory name, and `description`, at most 1,024 characters) followed by Markdown, plus optional `scripts/`, `references/` and `assets/`; the body should stay under 500 lines with detail loaded on demand ([Agent Skills specification](https://agentskills.io/specification)). Codex scans `.agents/skills` from the working directory upward and in the home directory ([OpenAI docs](https://learn.chatgpt.com/docs/build-skills)); Gemini CLI, Cursor and GitHub Copilot all read `.agents/skills/` as well ([Gemini CLI docs](https://geminicli.com/docs/cli/skills/), [Cursor docs](https://cursor.com/docs/context/skills), [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills)); Claude Code uses `.claude/skills`, which Cursor and Copilot also read. The de facto installer is Vercel's `npx skills add <owner>/<repo>`, which supports about 80 agents ([vercel-labs/skills](https://github.com/vercel-labs/skills)). The portable recipe is a public repository with the skill under `skills/<name>/`, all real work in self-contained command-line scripts that any agent with a shell (or a person) can run, no reliance on the experimental `allowed-tools` field, and, for chat clients with no shell, an optional thin MCP server wrapping the same scripts plus a paste-in prompt containing the DSL reference so that a tool-less LLM can at least emit a spec for the user to compile.

Licence and naming pitfalls are manageable if handled at design time. The table summarises what the research found; the reading that invoking a copyleft tool as a separate process does not relicense the skill is the researchers' interpretation, not legal advice.

On naming, Lottie is an open format stewarded by the Lottie Animation Community under the Linux Foundation, and no published trademark policy for the word was found, though the search was shallow and no trademark database was queried ([lottie.github.io](https://lottie.github.io/)). "LottieFiles", "dotLottie", "Lottie Creator", "Motion Copilot" and now "Lottie AI" are product names of Design Barn Inc. ([Lottie AI pricing](https://lottie.ai/pricing)). The precedent set by many independent MIT projects is descriptive use, so the low-risk course is a distinct project name with a phrase such as "text-to-Lottie skill", no LottieFiles branding, and an explicit non-affiliation line.

## The recommended build: one timeline spec, two emitters, one frame pipeline

The architecture that follows from the evidence has five stages. The agent first writes a **timeline spec**: a compact JSON or YAML document (or a short builder script) describing canvas, duration, frame rate, a tree of named elements with primitive shapes or imported SVG paths, and per-property keyframes with named easings. A zero-dependency **compiler** then emits two artifacts from that spec, Lottie JSON restricted to the 1.0.1 safe subset and a self-contained animated SVG using CSS keyframes with SMIL only for morphs. The **gates** run next: schema validation with warnings as errors, the semantic lint, and a frame render. The **review loop** produces a contact sheet of sampled frames and structured error messages that tell the agent exactly which spec line to fix. Finally the **exporter** turns frames into whichever raster format the destination needs, guided by a destination table like the one above. Node is the pragmatic single runtime, since the validator, the renderers, SVGO and Playwright all live there, although the `npx skills` installer's Node 22.20 requirement and Puppeteer's Node 22.12 floor mean the skill should document Node 22 as its baseline.

A suggested skill layout keeps `SKILL.md` short and procedural and pushes detail into references:

| Path | Purpose |
|---|---|
| `SKILL.md` | When to use, the five-stage workflow, output choices, hard rules |
| `references/spec.md` | Timeline spec grammar, easing presets, worked examples |
| `references/lottie-subset.md` | Allowed and denied Lottie features with reasons |
| `references/svg-rules.md` | SVG emitter rules and embedding contexts |
| `references/export.md` | Destination table, ffmpeg recipes, GIF caveats, licences |
| `scripts/compile.mjs` | Spec to Lottie JSON and animated SVG |
| `scripts/validate.mjs` | Schema check plus semantic lint, machine-readable errors |
| `scripts/render.mjs` | Lottie or SVG to RGBA PNG frames and a contact sheet |
| `scripts/export.mjs` | Frames to GIF, APNG, WebP, WebM, MOV, MP4; optional `.lottie` zip |
| `assets/preview.html` | Local player page for human review |

The build plan runs in five phases, each ending in something testable. Phase one is the compiler core: define the spec, implement the Lottie emitter for shape layers, groups, fills, strokes, gradients, trim paths, transforms, parenting and bezier easing, and wire in the schema validator and lint; the exit test is a corpus of twenty or so reference specs (bouncing ball, loader, checkmark draw, icon morph, staggered list) that all validate cleanly. Phase two is rendering and review: implement the frame renderer, starting with `@napi-rs/canvas` for speed and lottie-web in Playwright as the fidelity fallback, generate contact sheets, and confirm both renderers agree on the corpus. Phase three is the SVG emitter and its capture path, together with the browser tests this research left open: in-file CSS animation inside `<img>` across Chrome, Firefox and Safari, and the animation-safe SVGO config. Phase four is export: port the verified ffmpeg recipes, retest them on ffmpeg 9.x, add alpha verification and platform size checks, and add SVG path import (converting absolute cubic control points to Lottie's vertex-relative tangents) so users can ground animations in their own artwork. Phase five is packaging and evaluation: write `SKILL.md`, run `skills-ref validate`, test installation in Claude Code, Codex, Gemini CLI and Cursor, add the optional MCP wrapper, and publish first-pass success rates on a fixed prompt set, ideally the 900-sample MMLottieBench if its licence permits evaluation use.

## Conclusion

The strategic insight is that the hard part of "AI makes Lottie" was never the model; it is the representation and the feedback loop, and both are deterministic code that costs nothing to run. LottieFiles sells that code bundled with inference and a credit meter; a skill can ship the same code and let any model, on any plan the user already has, supply the inference. Because the checks are mechanical, the skill's reliability should also depend less on which model drives it than raw-JSON approaches do, which is exactly what "usable by any LLM" requires.

Three uncertainties should shape the first weeks of work rather than be argued about: no one has measured tool-assisted agent success on Lottie, the renderer and capture scripts in the research are untested sketches, and animated-SVG behaviour inside image contexts rests on secondary sources. All three resolve with a small test corpus, which doubles as the project's most persuasive asset. A public, reproducible pass rate against a fixed prompt set would be the first such benchmark for agentic Lottie generation and would distinguish this skill from both the paid product and the existing free one more convincingly than any feature list.
