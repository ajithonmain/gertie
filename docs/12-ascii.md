# ASCII animation

ASCII animation is frames of text characters on a fixed grid, played in sequence. It suits READMEs, terminal tools, retro-styled sites and social posts.

It is a separate engine from the vector pipeline. Lottie has no portable text support, so ASCII animation is not emitted as Lottie. Its outputs are animated SVG, the raster and video formats, and terminal playback.

## The ASCII scene file

Extension `.ascii.json`.

```json
{
  "ascii": 1,
  "name": "rocket",
  "cols": 40,
  "rows": 12,
  "fps": 8,
  "loop": true,
  "style": { "color": "#22c55e", "background": "#0b0f19", "fontSize": 16 },
  "frames": [
    { "text": [
      "                                        ",
      "                   /\\                   ",
      "                  /  \\                  ",
      "                  |  |                  ",
      "                 /|  |\\                 ",
      "                /_|__|_\\                ",
      "                   **                   "
    ], "hold": 2 }
  ]
}
```

| Field | Meaning |
|---|---|
| `cols`, `rows` | Grid size. Every frame is padded or reported if it exceeds this |
| `fps` | Frame rate. ASCII animation usually looks best at 6 to 12 |
| `frames[].text` | Array of strings, one per row |
| `frames[].hold` | How many frame intervals this frame is shown. Default 1 |
| `frames[].colors` | Optional. Per-row or per-cell colour overrides |
| `style` | Text colour, background, font size |

JSON strings need backslashes doubled. To spare the agent that, a frame may instead name a plain text file: `{ "file": "frames/01.txt" }`. A whole animation can also be one text file with frames separated by a line containing only `---`, loaded with `"framesFile": "rocket.txt"`. The text-file forms are the recommended way for an agent to write frames.

Lint rules: every row at most `cols` wide; at most `rows` rows; only printable characters; consistent frame count; a warning when `loop` is true and the last frame differs greatly from the first.

**Built in phase 8.** `cols` and `rows` are optional and default to the widest row and the tallest frame. A frame may give `text` as an array or as one string with newlines, or `file`. Error codes are `E-ASCII-*` (`JSON`, `SHAPE`, `VERSION`, `FIELD`, `NAME`, `SIZE`, `WIDTH`, `ROWS`, `CHAR`, `HOLD`, `FPS`, `LOOP`, `FRAME`, `FRAMES`, `NOFRAMES`, `FILE`, `COLOR`, `COLORS`, `STYLE`, `TOOMANY`, and `SOURCE`, `FX` and `LAYER` since phase 8b); warnings are `W-ASCII-WIDE`, `W-ASCII-FPS` (above 15; since phase 8b only under 80 columns), `W-ASCII-EMPTY` (every frame blank), `W-ASCII-STATIC` (every frame identical), `W-ASCII-LOOP-JUMP` and `W-ASCII-LARGE` (since phase 8b: above 400,000 cells, where there is no SVG). `W-ASCII-LOOP-JUMP` fires when the last frame differs from the first in more than 30 percent of cells and more than 2.5 times the average difference between neighbouring frames, so a loop that really is a loop, however busy, does not warn. A blank frame is not warned about on its own: scrolling text and rain have blank frames on purpose. `colors` on a frame is one entry per row; an entry is a hex colour for the whole row, a list with one colour per cell (`null` for the style colour), or `null`. Limits: 240 columns, 120 rows, 1200 frames. These remain the limits of inline frames; a recipe (phase 8b, part 3) allows 400 columns, 200 rows and 3600 frames.

## Ways to make frames

1. **The agent writes them.** Good for small, simple subjects. Models are reasonable at ASCII art up to about 40 by 15 and unreliable beyond that.
2. **Generated by procedure.** `gertie ascii gen` produces common effects from parameters: a spinner, a progress bar, scrolling text, a bouncing ball, rain, a starfield, a wave. These are computed, so they are exact.
3. **Converted from an image or video.** `gertie ascii from input.mp4 --cols 80` maps brightness to characters.
4. **Converted from a Gertie scene.** `gertie ascii from scene.gertie.json` renders the vector animation and converts the frames. This gives smooth, well-timed ASCII motion from a normal scene, and is often the best route.

### Brightness conversion

ffmpeg does the image work, so no image library is needed:

```bash
ffmpeg -i input.mp4 -vf "fps=10,scale=80:40,format=gray" -f rawvideo -
```

This writes one byte per cell per frame. Map each byte to a character from a ramp ordered from dark to light, for example:

```
 .:-=+*#%@
```

Details:

- Characters are about twice as tall as wide. To keep proportions, scale the height to half: for 80 columns from a 16:9 source, use about 22 rows (the code uses a 10 by 20 pixel cell, so it gives 23).
- `--invert` flips the ramp for dark text on a light background.
- `--ramp` accepts a custom ramp. A longer ramp gives finer tones.
- `--color` keeps each cell's colour from the source by reading a second, RGB pass.
- For sources with transparency, treat transparent cells as spaces.

**Verified in phase 8.** Raw frames are read from an ffmpeg pipe in Node with `scale=cols:rows:flags=area,format=rgba` and `-f rawvideo -pix_fmt rgba -`; the output is exactly `cols * rows * 4` bytes per frame and is split in Node. One RGBA pass replaces the two passes (gray, then RGB) described above: brightness is computed in TypeScript with Rec. 709 weights, colour and transparency come from the same bytes. Area averaging gives each cell the mean of its source pixels. Two ffmpeg facts found by running it: the `fps` filter drops the only frame of a still image unless it is `fps=N:eof_action=pass`, and a still image needs no `-t`. The aspect correction is tested: a 320 by 180 video at 40 columns is 11 rows, a square scene is 20 rows, and the ink of a converted circle is as wide as it is tall in pixels (ratio 0.8 to 1.25, `tests/browser/ascii-export.spec.ts`).

Vector scenes are converted by rendering frames in the browser (Lottie, at up to three times the size), decoding the PNGs, and averaging into cells in TypeScript. The conversion mode depends on the scene: a transparent scene is read by coverage (`alpha`, with a lift for dark colours so dark shapes still show), a scene with a solid background by distance from that background (`distance`), and pictures and video by brightness (`luma`). Cell colours for `--color` are rounded to 8 levels per channel, which keeps runs of one colour long and the SVG small. Identical neighbouring frames are folded into one frame with a longer `hold`.

## Output: animated SVG

Each frame is a `<g>` of `<text>` rows. All frames are stacked in the same place and shown one at a time with a stepped CSS animation.

```xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 416 256" width="416" height="256" font-family="ui-monospace,'SF Mono',Menlo,..." font-size="16" fill="#22c55e">
<style>.f{visibility:hidden;animation-duration:1500ms;animation-timing-function:step-end;animation-iteration-count:infinite}
.f0{animation-name:k0}@keyframes k0{0%{visibility:visible}8.33328333%{visibility:hidden}}
.f1{animation-name:k1}@keyframes k1{8.33328333%{visibility:visible}16.66661667%{visibility:hidden}}
@media (prefers-reduced-motion:reduce){.f{animation:none}.f0{visibility:visible}}</style>
<rect width="100%" height="100%" fill="#0b0f19"/>
<g class="f f0"><text x="98" y="23.2" textLength="20" lengthAdjust="spacingAndGlyphs" xml:space="preserve">/\</text></g>
</svg>
```

Rules, as built:

- A cell is a whole number of pixels: `round(fontSize * 0.6)` wide and `round(fontSize * 1.25)` high (10 by 20 at the default size 16), with a padding of `fontSize / 2`. The canvas is therefore a whole number of pixels, which matters for screenshots without a seam at the edge.
- Each row is split into runs of one colour. Every run is one `<text>` with `xml:space="preserve"`, an `x` at its own starting cell, and a `textLength` of its cell count times the cell width with `lengthAdjust="spacingAndGlyphs"`. Spaces never start or end a run, so empty space costs nothing. A run's text is escaped (`&`, `<`, `>`).
- Frames are `<g class="f fN">`. Each is visible for its share of the total time, with `step-end`, so there is no blending. A frame with `hold` n is visible for n intervals. A one-frame animation has no animation at all. With `"loop": false` the last frame carries an explicit `100%` visible keyframe and `animation-fill-mode: forwards`, so it stays on screen (without the explicit keyframe the held value is `hidden`: a bug found by the browser test).
- **Frame boundaries are moved 5 microseconds early.** When a renderer seeks a frame at exactly its start time, rounding in the browser can show the previous frame. This is the same problem as the vector emitter's (see `05-svg-emitter.md`); the shift is far below anything a viewer can see. A browser test seeks every interval, and the middle of every interval, at 5, 7, 8, 12, 24 and 30 fps with uneven holds, in Chromium and WebKit; with the shift set to zero it fails in both.
- Under `prefers-reduced-motion` a standalone SVG shows its first frame.

This output has no JavaScript and plays inside `<img>` and READMEs, like the vector SVG output.

To reduce size, rows that are identical between consecutive frames can be shared. Do this only if file size becomes a problem.

`--outline` converts glyphs to paths using a bundled open-licence monospace font, so the result looks identical everywhere. This needs a font parser (opentype.js, MIT) and belongs to a later version.

## Output: GIF and video

The ASCII SVG goes through the same renderer and exporter as everything else (`07-render-and-export.md`): the browser seeks it frame by frame, and ffmpeg encodes. Because the browser renders the text, the result matches the SVG.

For GIF, ASCII content compresses very well and has few colours, so GIF is a good format here, unlike for smooth vector art. A rocket at 216 by 296 pixels is a few kilobytes. GIF delays are whole hundredths of a second (see `07-render-and-export.md`), so 8 fps is rounded to 10 and 12 fps to 12.5, which makes timing wobble a little; the reference file tells the agent to prefer 10 fps for GIF.

The ASCII engine reuses the export pipeline unchanged: `exportScene` takes a frame source (`openFrames`) in place of a Lottie document, and the same quality ladders, destination limits and alpha checks apply. A transparent ASCII animation (`"background": "transparent"`) passes the alpha check in APNG, WebM and WebP. The 3.3 second bouncing-ball example is refused for Telegram (3 second limit) with the fix named; a 30-frame one fits.

## Output: terminal

`gertie ascii play rocket.ascii.json` plays in the terminal: clear the screen, print a frame, sleep, repeat. Use ANSI escape codes to move the cursor home between frames instead of clearing, to avoid flicker. Stop cleanly on Ctrl-C and restore the cursor.

`gertie ascii export --to sh` writes a self-contained shell script that plays the animation, so it can be shared without Gertie. `--to js` writes a small JavaScript module exporting the frames, for use in a command-line tool's loading indicator.

**As built.** `play` homes the cursor and ends every row with erase-to-end-of-line (`ESC[K`), so a shorter row never leaves the previous frame's characters behind; it hides the cursor, waits `hold / fps` per frame, stops on Ctrl-C or SIGTERM, and restores the cursor and colour on every path including an error (tested with an injected clock and stop signal). It refuses, with the size it needs, when the terminal is too small. When stdout is not a terminal it prints frame 0 and says so, and `--frame n` prints any one frame as plain text, which lets an agent that cannot see a terminal check a frame. The shell script uses only `printf`, `cat` with a heredoc whose tag no frame contains, and `sleep`; rows are padded with spaces instead of escape codes, and colour (the style colour, and per-cell colours when present) is plain ANSI truecolor. It passes `sh -n`, and a test runs it with a stub `sleep` and checks that the frames come out in order and the cursor is restored. `pause` falls back to `sleep 1` where `sleep` does not accept a fraction. The JavaScript module exports `frames`, `delays`, `fps`, `cols`, `rows`, `loop` and `start(stream)`, which does nothing when the stream is not a terminal and returns a function that stops it and restores the cursor; a test imports it and drives it with a fake stream. Frames in the module are plain text with no colour.

## What the agent does

This goes into `skills/gertie/references/ascii.md`:

- For a simple subject, write frames in a text file, 8 to 16 frames, at most 40 columns.
- For anything with smooth motion or a complex shape, write a normal vector scene with bold simple shapes, get it through `gertie qa`, and convert it with `gertie ascii from`.
- Keep the frame rate low. Eight frames per second reads as deliberate; thirty looks like noise.
- Check the result on the contact sheet before delivering it.

- *A vector scene converts to recognisable ASCII.* `pulse-circle` becomes a centred circle whose ink is as wide as it is tall (ratio 0.8 to 1.25); `rocket-launch` becomes a rocket whose ink starts low and rises by more than four rows. Looked at on screen as well: the circle and a rocket with fins and a window are clearly what they are at 40 to 50 columns.
- *The grid stays aligned in Chromium, Firefox and WebKit.* Passes in Chromium and WebKit: in rows of narrow (`i`), wide (`W`), punctuation and mixed text, every character starts within 1.5 pixels of its cell and every run is within 1 pixel of its length. Firefox is unrun (above).

**Findings that changed the design**

1. A one-shot animation with `animation-fill-mode: forwards` holds the value at 100%. Without an explicit `100%{visibility:visible}` on the last frame the last frame vanished. Found by the browser test, fixed in the emitter.
2. Frame boundaries must be shifted a few microseconds early so that a seek at exactly a frame's start time lands in that frame (see the SVG section). With no shift the timing test fails in Chromium and WebKit at 5 fps.
3. Inside an `<img>`, Chromium and WebKit do not apply the user's `prefers-reduced-motion` setting to the SVG, so it keeps playing there. As a standalone document the setting applies and the first frame shows. The reference says this plainly.
4. `ffmpeg`'s `fps` filter returns no frame for a single still image unless `eof_action=pass` is set.
5. The `W-ASCII-EMPTY` warning as first written ("a frame is blank") fired on the scroll and rain generators, which have blank frames on purpose. It now fires only when every frame is blank.

**Tests.** `tests/unit/ascii.test.ts` (31 cases: parse, lint, SVG text, boundaries, conversion, generators including seamless loops, terminal, shell and JavaScript exports, the command line), `tests/browser/ascii.spec.ts` (5 cases in Chromium and WebKit: alignment, timing at six frame rates, wrap and hold, `<img>` playback and reduced motion, canvas size), `tests/browser/ascii-export.spec.ts` (7 cases in Chromium: eight output formats with frame count, size and content, destinations and limits, transparency, conversion from scenes, video and images, colour).

**Not done**

- `--outline` (glyphs as paths) is a later version, as the design said.
- Rows shared between frames to shrink the SVG: not needed; the largest example is 21 KB.
- A converted video's brightness is not normalised per clip, so a dark video produces mostly dots. `--ramp` and `--invert` are the controls. (Done in phase 8b: `--normalize`, on by default for video and images.)
- An agent check (a subagent given only the skill files and asked for an ASCII animation) was not run for this phase.

## Dense and styled ASCII: design for phase 8b

All six tasks are built: 1 (conversion controls, part 1), 2 (cell styling, part 2), 3 (recipes, the canvas renderer and streamed export, part 3), 4 (effects in time, part 4), 5 (layers, part 5) and 6 (`ascii probe`, part 6, with the reference text and the five examples). The result of the phase is in `14-build-plan.md`, phase 8b. Everything above describes the phase 8 engine, which is good at small text art: up to about 80 columns, one colour or simple colour, 6 to 12 frames per second. The project owner supplied five reference videos of the kind of ASCII animation people share today, and the engine cannot make any of them. This section says what they show, what is missing, and how to add it. Tasks and acceptance checks are in `14-build-plan.md`, phase 8b.

### What the references show

The clips were studied with contact sheets and enlarged crops. They are other people's work and are not in the repository; the corpus examples for this phase must be original art.

| Clip | What it is | What makes the look |
|---|---|---|
| A bouquet that grows and blooms, then butterflies leave | About 200 columns, 30 fps, 16 seconds | Dense small glyphs from a long ramp, a three-colour palette by part (green stems, pink and white flowers), a soft glow like a CRT, and real animation underneath: stems draw upward, flowers pop open in turn |
| Flower photographs | Portrait, 108 seconds | Three renderings of the same pictures: coloured dots whose colour carries the image, random letters and digits coloured per cell, and sparse-to-dense reveals where cells appear a few at a time |
| A koi pond | About 180 columns, 30 fps | Several independent sprites (fish, lily pads, ripples, a panel of code) moving over one another, cells with a coloured background behind the glyph, so shapes read as solid |
| An After Effects breakdown of a hand | Tutorial | The recipe itself: split brightness into four bands, give each band one shape (a filled circle, an X, a 1, a slash), and tint the cells along the outline with an accent colour |
| A blue flower that turns on its stem | 24 fps, landscape | A chosen character set (C, Z, triangles, stars, rings) instead of a brightness ramp, a gradient sky that is not made of characters, a glow, and small typed captions |

### What is missing, in one list

1. **Density.** Frames are stored as text in JSON and drawn as one SVG holding every frame. At 200 columns, 30 fps and 10 seconds that is 300 frames of 20,000 cells: far too large for either. The limits (240 columns, 1200 frames) and the `W-ASCII-FPS` warning above 15 fps assume small art.
2. **Control over conversion.** There is a ramp, `--invert` and `--color`. There is no brightness normalisation (noted as not done in phase 8), no way to drop a background, no palette, no character set that is not a ramp, no outline accent.
3. **Cell styling.** A cell is a character in a colour. The references also use a background colour per cell, dots or squares instead of characters, a glow, and a gradient behind everything.
4. **Effects in time.** Reveals, decoding, shimmer, typing. Today the only motion is whatever the source frames contain.
5. **Composition.** One grid, no layers. The pond cannot be built.
6. **Reading a reference.** Nothing tells the agent the grid size, character set or palette of a clip it is asked to imitate.

### Design

Six additions. Each is independent enough to build and test alone, in this order.

#### 1. Conversion controls

All in `src/ascii/convert.ts` as pure functions over the RGBA cells that `media.ts` already produces; the command-line flags are read in `src/cli/lib/ascii-command.ts`. They apply to every `ascii from` source (video, image, GIF, vector scene).

| Flag | Meaning |
|---|---|
| `--normalize` | Stretch brightness so the 2nd percentile of the whole clip maps to 0 and the 98th to 1. Two passes over the frames, or one pass keeping a 256-bin histogram. On by default for video and images, off for vector scenes |
| `--gamma n` | Applied to the 0 to 1 value after normalising. Default 1. Below 1 lifts dark areas |
| `--threshold n` | Cells whose value is under `n` (0 to 1) become spaces. Default 0 |
| `--key auto` or `--key #hex` | Cells within a colour distance of 40 (of 441) from the key colour become spaces. `auto` takes the median colour of the outermost ring of cells of the first frame. This is what puts a subject on black |
| `--crop x,y,w,h` | Source pixels, by ffmpeg, before scaling |
| `--color-levels n` | Levels per channel for `--color`, 2 to 32, default 8 |
| `--palette #a,#b,...` | Each coloured cell takes the nearest palette colour (distance in RGB). Implies `--color` |
| `--tint #hex` | One hue: the cell colour is the tint scaled by the cell's value, from 35 percent to 100 percent. Implies `--color`, excludes `--palette` |
| `--ramp name` | Named ramps beside a literal one: `standard` (the current default), `long` (` .'`^",:;Il!i><~+_-?][}{1)(|/tfjrxnuvczXYUJCLQ0OZmwqpdbkhao*#MW&8%B@$`), `blocks` (` ░▒▓█`), `dots` (` ·∙•●`), `binary` (` 01`), `digits` (` 1732456908`), `bands` (` /1X●`). **Verified (task 1):** every character of every named ramp is one cell wide: its natural advance, measured with no `textLength` at 160 px, is within 2 percent of the advance of `M` in Chromium (Google Chrome) and WebKit on macOS, so none were dropped. The check is the browser test "every character of every named ramp is one cell wide" in `tests/browser/ascii.spec.ts`. **Not verified:** Windows and Linux fonts (Consolas, DejaVu Sans Mono, Liberation Mono), and Firefox, whose Playwright build does not start on the development machine. The test is ready for them: `GERTIE_BROWSERS=firefox npm run test:browser`. Where a viewer's font lacks a character, the SVG's fixed `textLength` still keeps the grid aligned, so the worst case is a squeezed or fallback glyph, not a shifted row |
| `--chars set` | A character set that is not a ramp. Every non-empty cell takes a character from `set` chosen by a hash of its column, row and `--seed`, so it is the same on every frame and does not flicker. Brightness then shows only through colour, so this implies `--color` unless `--tint` or `--palette` is given |
| `--shimmer n` | With `--chars`: the fraction of non-empty cells (0 to 1) that re-roll their character on each frame. Default 0. The choice of which cells is a hash of column, row and frame |
| `--dither ordered` | Add a 4 by 4 Bayer offset of plus or minus half a ramp step before picking the character. Smooths gradients with short ramps |
| `--edge-color #hex` | Cells whose value differs from a 4-neighbour's by more than 0.35 take this colour. The outline accent of the hand clip |

A cell is empty when it is a space after `--threshold` and `--key`. Order of operations: crop, scale to cells, key, normalise, gamma, threshold, dither, character, colour, edge colour.

**As built (task 1).** The controls are pure functions in `src/ascii/convert.ts`: `convertClip(frames, cols, rows, options)` converts a whole clip (normalising and `--key auto` need every frame, the first frame for the key) and `cellsFromRgba` is the one-frame form of it. `media.ts` does `--crop` through ffmpeg's `crop` filter, before `fps` and `scale`. Details the table does not say:

- **Default and normalising.** With none of the new flags the output is byte-identical to phase 8 (a unit test compares the converter's output on a random raster, in all three modes, with the hashes taken before the change; the command line was compared on `pulse-circle`, with and without `--color`). The one deliberate change: `--normalize` is **on by default for video and images** (turn it off with `--no-normalize`), so a dark clip no longer converts to mostly dots, and those conversions now look different from phase 8. It is off by default for vector scenes, whose colours are already the intended ones; `--normalize` turns it on.
- **Normalising.** A 256-bin histogram of cell values (after the mode and `--invert`, so for brightness, coverage or distance) over every frame, leaving out keyed cells and, in brightness and coverage mode, transparent ones. The 2nd and 98th percentiles are the bin positions (steps of 1/255). A picture whose two percentiles are less than 1/255 apart is left as it is.
- **Key.** Distance is Euclidean in RGB on the cell colour, 40 or less is keyed. `auto` is the per-channel median of the outermost ring of cells of the first frame only. Keyed and thresholded cells are written as a space, not as the first character of the ramp.
- **Gamma** is 0.1 to 10. **Threshold** compares the value after gamma.
- **Colour.** `--color-levels n` (2 to 32, whole) rounds each channel to `n` levels and needs `--color`, `--chars`, `--palette` or `--tint`. Without it the phase 8 rounding (steps of 32, 8 to 9 distinct values) is kept, which is what makes the default byte-identical. `--palette` picks by RGB distance from the unrounded cell colour, and `--color-levels` has no effect with it (an error). `--tint` scales by the cell value after gamma. `--palette`, `--tint` and `--chars` each imply `--color`.
- **Chars.** The set may not contain spaces. A cell whose value is 0, or that is keyed or under the threshold, stays a space. The character of a cell is `set[floor(h * n)]` with `h` a hash of column, row and seed, so it does not change from frame to frame. `--chars` excludes `--ramp` and `--dither`; `--seed` and `--shimmer` need `--chars`.
- **Shimmer.** On each frame a cell is chosen when a hash of column, row, frame and seed is under the fraction, and a chosen cell takes one of the *other* characters of the set (so the stated fraction really does change on every frame; with a one-character set nothing can change). Which cells are chosen is repeatable.
- **Hash.** `cellHash(...integers)` mixes its arguments into a seed and returns the first number of `mulberry32` from `src/ascii/gen.ts`. There is no `Math.random` in the converter.
- **Dither.** The Bayer 4 by 4 matrix gives each cell an offset of `((m + 0.5) / 16 - 0.5)` ramp steps, applied to cells that are not empty. Black and white cells keep their end characters.
- **Edge colour** is decided from the cell values after threshold: a cell that is not a space takes the colour when any 4-neighbour differs from it by more than 0.35 in value. It wins over the other colour controls. This includes steps inside a shape, such as between two bands of the `bands` ramp, not only the silhouette.
- **Ramps.** A `--ramp` value that is the name of a named ramp selects it; any other value is a literal ramp. The `long` ramp has 69 characters.
- **Crop for vector scenes.** `--crop x,y,w,h` is in scene pixels; the scene is rendered at its usual scale and the rectangle is cut from the rendered picture (`cropRaster`) before it is averaged into cells, because there is no video for ffmpeg to crop. Rows are computed from the cropped size.
- **Errors.** Bad values, a rectangle outside the source, and the excluded combinations (`--tint` with `--palette`, `--chars` with `--ramp` or `--dither`, `--shimmer` or `--seed` without `--chars`, `--color-levels` without colour, `--normalize` with `--no-normalize`) exit 2 with a message that names the flag and the fix.

#### 2. Cell styling

New optional `style` fields in the `.ascii.json` file, drawn by both renderers (the SVG emitter and the canvas renderer of part 3):

| Field | Meaning |
|---|---|
| `glyph` | `"text"` (default), `"dot"` or `"square"`. With `dot` and `square` nothing is drawn as a character: each non-space cell is a filled circle or square whose size is the character's position in `ramp`, from 25 percent of the cell for the first non-space entry to 95 percent for the last. In SVG these are `<circle>` and `<rect>` |
| `ramp` | The ramp the frames were made with. Required when `glyph` is not `text` (`E-ASCII-STYLE` without it) |
| `cellAspect` | Height over width of a cell. Default 2. `1` gives a square grid, which is what dots and squares want; `ascii from` then computes rows with aspect 1 |
| `background` | Also accepts `{ "from": "#hex", "to": "#hex", "angle": degrees }` for a linear gradient behind the grid |
| `glow` | 0 to 1. Default 0. A blurred copy of the glyph layer added under the sharp one: blur radius `glow * fontSize`, opacity 0.6. In SVG an `feGaussianBlur` filter on a `<use>` of the frame group; in canvas a `blur()` canvas filter on the glyph layer (not `shadowBlur`: see part 3, "As built"). **Verified (task 2):** an SVG with the glow filter still plays inside an `<img>` in Chromium (Google Chrome) and WebKit: the three frames of a test animation each appear over 1.5 seconds, the natural size is the canvas size, and the SVG still passes `svgProblems` (no script, handler, foreignObject or external reference; the `href` of the `<use>` is internal). The glow is visible: a pixel just above a block of glyphs is lighter than the background with glow, and exactly the background without it. So glow stays in SVG and `ascii export --to svg` needs no restriction. **Cost** (browser test "glow cost", a worst case of 120 by 40 cells where every cell is a glyph in one of four colours, so about 4800 text runs per frame, measured as seek plus screenshot, two test workers running at once, on the development Mac): Chromium 688 ms per frame without glow and 862 ms with it (25 percent more); WebKit 1481 and 2156 ms (46 percent more). The filter is a real cost on dense grids, and it is paid per frame by the exporter; for large grids the canvas renderer of part 3 is the planned path. Not measured: Firefox (its Playwright build does not start here), and playback speed in a viewer's own browser |

A frame gains `backgrounds`, in the same shape as `colors` (one entry per row; a colour, a per-cell list, or `null`): a colour filled behind the cell. `ascii from` writes it with `--cell-bg n`, where `n` (0 to 1, typically 0.35) is how bright the fill is relative to the cell's own colour. Lint: same checks as `colors`, code `E-ASCII-COLORS`.

**As built (task 2).** The fields, the parsing and the SVG emitter are in `src/ascii/types.ts`, `parse.ts` and `svg.ts`; `ascii from` writes them; the terminal outputs are in `terminal.ts`.

- **Style fields.** `glyph`, `ramp`, `cellAspect` (0.5 to 4), `glow` (0 to 1) and a gradient `background` are read in `parse.ts`; every problem is `E-ASCII-STYLE` (a bad colour inside the gradient is `E-ASCII-COLOR`) and names the field, the problem and the fix. `ramp` is required when `glyph` is `dot` or `square`, and with those glyphs a non-space character that is not in the ramp is an error that names the frame, row, column and character, because its size would be unknown. `ramp` must be a literal string, not a ramp name. A gradient has `from`, `to` and `angle` (degrees, CSS convention: 0 up, 90 right, 180 down, default 180). The parsed style keeps the `from` colour as `background`, so flattening, the alpha checks and destination limits see an opaque background.
- **Cell shape.** At `cellAspect` 2, the default, a cell is `round(fontSize * 0.6)` by `round(fontSize * 1.25)` pixels, exactly as in phase 8. At any other aspect the height is `round(width * cellAspect)` and the text baseline is 76 percent of the cell down (it is `fontSize * 0.95` at the default). Every cell is a whole number of pixels.
- **Frame `backgrounds`.** The same shapes as `colors` (one entry per row: a colour, a list with one entry per cell, or `null`), linted with the same checks under `E-ASCII-COLORS`, and the messages say `backgrounds` where they would say `colors`. An empty frame field and `null` are the same.
- **Dots and squares.** One `<circle>` or `<rect>` per non-space cell, centred in the cell, with a diameter or side of `size * min(cell width, cell height)`. `size` runs from 0.25 for the first non-space entry of the ramp to 0.95 for the last, evenly by position; with one non-space entry it is 0.95. The fill is the cell's colour, or the style colour inherited from the `<svg>`. No `<text>` is written.
- **Cell backgrounds.** One `<rect>` per run of equal colour along a row, so neighbours with the same colour merge and cost one element. They are painted first in the frame group, so they sit behind the glyphs. The rects are whole pixels, so there is no seam between merged cells (browser test).
- **Gradient.** A `<linearGradient>` in `<defs>` in user space, with the CSS line length for the angle, and the background `<rect>` filled with `url(#gertie-bg)`. The reference is internal, so `svgProblems` still passes.
- **Glow.** `<defs>` holds one filter (`feGaussianBlur`, `stdDeviation = glow * fontSize`, over the whole canvas) and each frame group holds a `<use href="#gertie-glow-N">` at opacity 0.6 followed by the group of glyphs it copies. Cell backgrounds are outside the copy, so only glyphs glow. A frame with no glyphs has no `<use>`.
- **`ascii from`.** `--glyph text|dot|square`, `--cell-aspect n` (the row count is computed for that aspect, so `1` gives square cells), `--cell-bg n` (0 to 1: each non-empty cell gets a background of its own colour, as rounded for the SVG, times `n`; a cell with no colour of its own uses the style colour), `--glow n` and `--font-size n` (6 to 64; the cell size follows it). With `dot` or `square` the ramp used is written to `style.ramp`. Fields at their default are not written, so a file made without the flags is the same as before. `--glyph dot` and `--glyph square` cannot be combined with `--chars`: a character set is not ordered, so it has no sizes.
- **Terminal.** `ascii play` and the shell script ignore `glyph`, `ramp`, `cellAspect`, `glow` and a gradient: they draw the characters. Cell backgrounds are drawn, as ANSI truecolor background colours (`ESC[48;2;r;g;bm`), also behind spaces; a row that ends on a background resets it (`ESC[49m`) before erase-to-end-of-line so the fill does not run to the edge of the terminal, and a row with backgrounds keeps its trailing spaces. `--no-color`, `play --frame` and the JavaScript module are plain text and show no backgrounds. The shell script uses colour when any frame has per-cell colours or backgrounds.
- **Phase 8 files.** Every file in `examples/ascii/` lints clean and exports to the same SVG, byte for byte, as before the change (compared by exporting each to svg before and after). An animation with none of the new fields has no `<defs>`, `<use>`, `<circle>` or extra `<rect>` (unit test).

#### 3. Large grids: a recipe file, a canvas renderer, streamed export

**Decision.** A dense animation is not stored as frames. Its `.ascii.json` names its source and how to convert it, and frames are computed when it is rendered or exported:

```json
{
  "ascii": 1,
  "name": "bouquet",
  "fps": 24,
  "loop": true,
  "style": { "background": "#000000", "fontSize": 8, "glow": 0.5 },
  "source": { "file": "bouquet.gertie.json", "cols": 180, "ramp": "long", "palette": ["#7cb342", "#f48fb1", "#f5f5f5"], "key": "auto" },
  "fx": [ { "effect": "reveal", "by": "rows-up", "at": 0, "duration": 2 } ]
}
```

- `source` takes `file` (a vector scene, video, GIF or image, relative to this file) and every conversion control of part 1 by its flag name in camel case. `frames`, `framesFile` and `source` are mutually exclusive (`E-ASCII-FRAMES`). `ascii from ... --recipe` writes this form instead of frames; it is the default when `cols * rows * frames` would exceed 400,000 cells.
- The reason is size and editability: the recipe is a few lines the agent can change and re-run, and a 200 column clip never becomes a 50 megabyte JSON file.
- **Reading frames.** One async generator, `framesOf(scene)` in `src/ascii/`, yields `{ cells, colors, backgrounds, hold }` per frame for all three forms, after effects (part 4) and layers (part 5). File and process access for `source` stays in `src/cli`, passed in as a function, as `resolveIncludes` does for vector scenes.
- **Canvas renderer.** A page `skills/gertie/assets/ascii-render.html`, loaded by the existing Playwright renderer. It exposes `draw(frame, style)`, which paints one frame on a `<canvas>` sized to the grid: gradient or solid background, cell backgrounds, then glyphs with `fillText` at cell centres (or arcs and rects for `dot` and `square`), then glow. The exporter calls it once per frame and screenshots the canvas. No frame is kept in the page. **Verify during build:** frames per second of this loop at 200 by 100 cells with colour; if it is under 5, batch the screenshot through `canvas.toBlob`. **Verified (task 3):** under 5, so the capture is batched through `canvas.toBlob`. Measured on the development Mac in Google Chrome, 200 by 100 cells at font size 8 (a 1008 by 1008 pixel canvas), draw plus capture plus transfer to Node, per frame: with a screenshot per frame and colours sent as one string per cell, **1.7 fps** (585 ms: 150 ms to send the frame to the page, 70 ms to paint, 265 ms for the screenshot). With colours packed as a table and one index string per row, text drawn in runs, and eight frames per call captured with `toBlob`: **3.6 fps** in the worst case (every cell a random glyph of the `long` ramp in a random one of 512 colours, so there are no runs and each PNG is 1.6 MB; 3.1 fps with glow), **16.4 fps** on a dense coloured video (`testsrc` with `--color --ramp long`, 11.7 with glow 0.5) and **42.6 fps** on a converted vector scene (`night-sky` with `--color`). Real conversions have runs of one colour; only noise reaches the worst case, and there the PNG encoding, not the drawing, is the cost.
- **Choice of renderer.** Up to 400,000 cells in total the SVG path is used as now, so small animations keep their README-ready SVG. Above that, raster and video exports use the canvas renderer, and `--to svg` is refused with `E-ASCII-TOOMANY` and the fix "export to mp4, webm or gif, or lower cols, fps or the duration". The two renderers must agree: a browser test draws one small coloured frame both ways and allows 2 percent of pixels to differ.
- **Limits and lint.** Inline frames keep today's limits. A recipe may have up to 400 columns, 200 rows and 3600 frames. `W-ASCII-FPS` fires above 15 fps only when the grid is under 80 columns: dense grids converted from smooth sources look right at 24 to 30.
- `ascii render` (the contact sheet) and `ascii play` go through `framesOf` too. `play` refuses a grid larger than the terminal, as now.

**As built (task 3).** `src/ascii/recipe.ts` (the `source` field), `src/ascii/frames.ts` (`shapeOf`, `framesOf`, `collect`), `src/cli/lib/ascii-source.ts` (the reader), `src/render/ascii-canvas.ts` and `skills/gertie/assets/ascii-render.html` (the canvas renderer). Details the design does not say, and the decisions taken:

- **`source`.** Fields: `file`, `cols` (4 to 400, default 80), `rows` (1 to 200; absent means computed from the source's proportions and `style.cellAspect`, capped at 200), `maxSeconds` (0.1 to 120; absent means 10 seconds of a video and the whole of a vector scene, as in `ascii from`), `ramp` (a name or a literal ramp), `invert`, `color`, `normalize` (absent means on for media and off for vector scenes), `gamma`, `threshold`, `key` (`"auto"` or a colour), `crop` (`[x, y, w, h]`), `colorLevels`, `palette` (a list of colours), `tint`, `chars`, `seed`, `shimmer`, `dither`, `edgeColor`, `cellBg`. Every problem with a field is a new code, **`E-ASCII-SOURCE`**, naming `source.<field>`, the problem and the fix, with the nearest name for an unknown field; the combinations `ascii from` refuses are refused with the same reasons. A missing file is `E-ASCII-FILE`, a vector scene that does not compile is `E-ASCII-SOURCE` with its first errors, and a crop outside the source is `E-ASCII-SOURCE` once the source is opened. With `source`, `cols` and `rows` at the top of the file are `E-ASCII-SIZE` with the fix "move it into source": the grid of a recipe is set in one place. The styling flags (`glyph`, `cellAspect`, `glow`, `fontSize`) stay in `style`. A recipe has none of the warnings about frame content (blank, static, loop jump), because it has no frames until rendered.
- **`framesOf(scene, read)`** yields inline frames as they are, and converts a recipe one frame at a time. `read(file)` is the only way it reaches the source; it returns an `OpenSource` with the kind (`scene` or `media`), the size, the length, a vector scene's background, a `frameCount` and `cells(request)`, an async iterable of cell pixels. Normalising needs the whole clip, so with `normalize` on, `framesOf` reads the source twice: one pass for the histogram, one to convert (the converter was split into `startClip`, `addToClip`, `finishClip` and `convertFrame` for this; `convertClip` is now built from them and gives the same output). Identical neighbouring frames are folded into one frame with a longer hold exactly as `ascii from` folds them, and a source that ends early holds its last frame, so the holds always add up to the planned frame count, which the exporter needs before the first frame is drawn. `shapeOf(scene, read)` gives the grid, the frame count and the renderer without converting anything; for media the frame count comes from running ffmpeg with the same filters at one pixel per frame. Neither `frames.ts` nor `recipe.ts` imports a file or process module (a unit test checks).
- **The reader** (`src/cli/lib/ascii-source.ts`) compiles a vector scene and draws it in the browser as `ascii from` did, or streams a video, GIF or image out of ffmpeg one frame at a time (`streamFrames` in `media.ts`) instead of reading the whole clip into memory. The paths in a recipe are relative to the recipe; `ascii from --recipe` writes the source relative to the output file, or absolute when the two share nothing but the root.
- **One path for both forms.** `ascii from` without `--recipe` now converts by building the same recipe in memory and collecting `framesOf`, with the phase 8 inline limits (computed rows capped at 120, frames at 1200). Its output is byte for byte the same as before on eight cases (vector scenes with and without colour, palette, glow, cell backgrounds and the long ramp, crop, normalise and dither, an image as dots, a video with key, gamma, `--chars` with shimmer and edge colour, and tint with threshold). One of them, `rocket-launch` with the `long` ramp, gives one of two outputs that differ in one cell from run to run; the phase 8 build does the same (three runs of the old bundled script gave both), so this is browser rendering noise at a ramp step, not a change.
- **`ascii from --recipe`** writes the recipe: the style on one line and one source field per line, defaults left out, the ramp by name. It is also chosen without the flag when the grid is wider or taller than inline frames allow (more than 240 columns or 120 rows), or when cols times rows times frames is more than 400,000; `ascii from` then says why. `--cols` now accepts up to 400 and `--rows` up to 200 for this reason. The written recipe is linted at once, which opens the source and prints its grid, length and renderer.
- **Speed of reading a vector scene.** Rendering the scene was not the slow part; decoding was: `decodeImages` sent every pixel of a 1536 by 1152 frame back to Node as base64 built by hand, about 636 ms a frame. Two changes: `decodeImages` now uses the browser's own base64 encoder (`FileReader`), the same bytes faster (430 ms), and the scene reader averages each rendered frame into cells inside the page, by running the very same `cropRaster` and `downsample` functions there (their source text is passed to the page), so only `cols * rows * 4` bytes come back. A 32 frame contact sheet of a 200 by 100 recipe went from 31 to 13 seconds, and the conversion output is unchanged (the eight cases above).
- **Choice of renderer.** "Frames" in the 400,000 rule is the frames stored, for inline frames (a frame held 600 times costs one frame of SVG), and the frames computed before folding, for a recipe (the stored count is not known before converting). Above the limit `export` uses the canvas renderer for every raster and video format and refuses `svg` with `E-ASCII-TOOMANY` and the design's fix. **Decision:** it also refuses `sh` and `js`, which hold every frame as text just as the SVG does, and `--for readme`, whose formats include `svg` (the fix then adds "use --to instead"). This applies to inline frames over the limit too, and `W-ASCII-LARGE` now fires above 400,000 cells and says this, instead of above 600,000 as "a large SVG".
- **Streamed export.** The exporter is unchanged: `openFrames` returns a frame renderer (`openCanvasFrames`) that pulls frames from `framesOf` as the exporter asks for them in order, draws eight at a time, and reuses the picture of a held frame. Nothing is kept: the page repaints the whole canvas for each frame, and Node keeps at most one batch of PNGs. `ascii render` uses the same renderer for the picked frames (it converts every frame up to the last one picked, since folding and the normalising pass need them), and makes the sheet with `render.html` in a second page.
- **The canvas page.** It is dark when opened by itself and transparent while Gertie captures, so a transparent animation stays transparent. **Decision:** text is drawn in the same runs as the SVG, each run stretched to exactly its cell count times the cell width (what `textLength` with `spacingAndGlyphs` does), not one `fillText` per cell at the cell centre as the design said: it matches the SVG more closely and is faster. **Decision:** the glow is a `blur()` canvas filter of standard deviation `glow * fontSize` on a separate glyph layer drawn at 0.6 opacity under the sharp layer, the same Gaussian as the SVG's `feGaussianBlur`, not `shadowBlur`, which paints every shadow in one colour. The canvas is drawn at the export scale (`deviceScaleFactor`), so `--scale 2` is sharp.
- **The renderers agree** (browser test `tests/browser/ascii-canvas.spec.ts`): on a 30 by 8 frame of mixed characters in five colours with cell backgrounds, no pixel differs by more than 48 of 255 in any channel between the SVG and the canvas, as text, text with glow, text on a gradient at font size 12, dots on square cells, and squares (0.00 percent; the limit is 2). Pixels that are not exactly equal, from anti-aliasing: 9 percent for text, 74 percent with glow (the two blurs differ in their last bits), 12 to 13 percent for the others. As a control, the same frame with other characters differs in 20.6 percent.
- **`ascii play`** checks the grid against the terminal before converting anything. A recipe within the SVG limit is converted once and kept; a larger one is converted again on every pass through the loop, so it never sits in memory, and a vector scene source may then not keep up with the frame rate. `--frame n` and the frame 0 shown when stdout is not a terminal convert only up to that frame.
- **Timing** (acceptance check). A 180 column, 24 fps, 8 second recipe of an 8 second, 640 by 360 vector scene with four moving shapes (`long` ramp, a four-colour palette, glow 0.4, font size 8; 180 by 51 cells, 192 frames, canvas renderer) exported to MP4 in **28.7 seconds** on the development Mac (908 by 518 pixels, 192 frames, 1.5 MB). Its `.ascii.json` is **292 bytes**. A 160 column recipe of `rocket-launch` at 24 fps (100 rows, 58 frames) exports to MP4 with 58 frames at the canvas size in the browser test.
- **Not verified.** The canvas renderer runs only in Chromium, which is what the exporter uses; it was not tried in WebKit or Firefox. The frame rates above are from one machine. `ascii play` of a recipe was tested through `--frame` and the non-terminal path, not by watching it in a terminal.

#### 4. Effects in time

`fx` is a list on the scene, applied in order by a pure function `applyFx(frames, fx, fps)` in `src/ascii/fx.ts`. Each entry has `effect`, `at` (seconds, default 0) and `duration` (seconds). `ascii fx <file> --effect ... ` appends an entry to a file. Every effect works per cell from a threshold `t` in 0 to 1 that is fixed for the cell, and a progress `p` that runs 0 to 1 over the effect's time.

| Effect | Parameters | Rule |
|---|---|---|
| `reveal` | `by`: `scatter` (t is a hash of column, row, seed), `rows-up`, `rows-down`, `cols-right`, `cols-left` (t is the position along that axis), `radial` (distance from the centre of the non-empty cells, normalised), `bright-first` (1 minus the cell's value); `seed` | A cell is empty while `p < t`. Before `at`, everything is empty |
| `hide` | The same `by` values | The reverse: a cell becomes empty once `p >= t` |
| `decode` | `chars` (default the scene's ramp without the space), `seed` | While `p < t` the cell shows a character from `chars` re-rolled every frame, in its final colour; after that, its own character |
| `shimmer` | `amount` 0 to 1, `chars`, `seed` | Over the effect's time, that fraction of non-empty cells shows a re-rolled character each frame. For looping life in a still picture |
| `type` | `cps` characters per second (default 30) | For text layers (part 5): cells appear in reading order at that rate, with a block cursor `█` on the newest cell. `duration` is ignored. **Built in task 5**; see part 5, "As built" |

Hashes use the existing `mulberry32` seeded per cell, so output is repeatable. An effect never changes colours. Lint: `E-ASCII-FX` for an unknown effect or parameter (with the nearest name), and for a time range outside the animation.

**As built (task 4).** `src/ascii/fx.ts` holds `parseFx`, `checkFxRange` and `applyFx`; `framesOf` applies a scene's `fx` after reading its frames, for inline frames, a `framesFile` and a recipe alike, so `render`, `play` and `export` all show the effects. Details the table does not say, and the decisions taken:

- **Time.** Interval `k` is at `k / fps` seconds and progress is `p = (k / fps - at) / duration`, clamped to 0 to 1. A frame with a `hold` of n covers n intervals. While an effect runs, each of its intervals gets a frame of its own (hold 1), because the picture changes; before and after it a held frame stays one frame, so the holds always add up to the length of the input, and the SVG path counts such a scene as one frame per interval when it chooses a renderer. `applyFx(frames, fx, fps, { ramp, cellAspect })` takes any iterable or async iterable and yields as it goes, holding only the frame it is working on. **Change from the design:** it has an optional fourth argument, because `decode` and `shimmer` need the scene's ramp and `radial` needs the cell shape; `framesOf` passes `style.ramp`, else the recipe's `source.ramp`, else the standard ramp, and `style.cellAspect`.
- **Thresholds** `t` (0 up to, not including, 1) of a non-empty cell: `scatter` a hash of column, row and seed; `rows-up` `(rows - 1 - row) / rows`, so the bottom row is 0; `rows-down` `row / rows`; `cols-right` `col / cols`; `cols-left` `(cols - 1 - col) / cols`; `radial` the distance from the centre (mean position) of the frame's non-empty cells, with a row counting `cellAspect` times a column, divided by the largest such distance; `bright-first` 1 minus the cell's value, which is the place of its character in the ramp, or, for a character that is not in it, the brightness of its colour, or full. The rule is the table's: a `reveal` cell is empty while `p < t`, so a cell with `t = 0` is shown from the first interval of the effect; a `hide` cell is empty once `p >= t`.
- **Outside the effect.** `reveal` is empty before `at` and untouched from `at + duration`; `hide` is untouched before `at` and empty from `at + duration`. **Decision:** `decode` and `shimmer` are untouched before `at` as well as after the end (the design gave no rule for before `at`, and re-rolling every frame before it starts would split a held frame into a frame per interval for no visible reason; start a decode at 0 to have it scrambled from the first frame).
- **Decode and shimmer.** Decode: a cell has a threshold from a hash of column, row and seed; while `p < t` it shows `chars[hash(column, row, interval, seed)]`, so it changes every interval, and settles for good once `p >= t`. Shimmer: on each interval a cell is chosen when a hash of column, row, interval and seed is under `amount` (default 0.1), and it takes another character of the set than its own (as `--shimmer` does in part 1), so the stated fraction really changes. Spaces are never touched. Default `chars` is the ramp without the space.
- **What an effect changes.** Characters, and the background of a cell that `reveal` or `hide` empties, so no fill is left behind. Never a colour: the colour grid of a frame is the very same object after any effect (a unit test compares it).
- **`fx` entries.** `at` defaults to 0. `duration` is required for every effect but `type` (`E-ASCII-FX`, with the fix), and must be above 0. `by` defaults to `scatter`, `seed` to 0, `amount` to 0.1, `cps` to 30. A parameter that the effect does not take (`amount` on `reveal`) is `E-ASCII-FX` naming the parameters it takes; an unknown effect, parameter or `by` gets the nearest valid name. `type` is parsed and then ignored by `applyFx` unless it is given `typing` (part 5 does that for text layers); since task 5 a `type` in the scene's own `fx`, or in the `fx` of a layer that is not a text layer, is `E-ASCII-FX` with the fix "move it into the fx of a text layer". A range outside the animation (`at` at or after the end, or `at + duration` past it) is `E-ASCII-FX` with the fix, at parse time for inline frames and when the source is opened for a recipe (which is when its length becomes known; `ascii lint` does that).
- **`ascii fx`** adds `{"effect", ...}` to the file as text, so the rest of the file keeps its layout (one row per line), and then lints it. `--duration` defaults to the rest of the animation after `--at`. **Change from the design:** if the new entry would be an error (a range outside the animation), the file is left as it was and the error is printed, instead of writing it and then reporting it. `--effect type` is refused (since task 5 the message says it belongs in a text layer's `fx`, which `ascii fx` does not edit). A bad flag, or a flag the effect does not take, is a usage error (exit 2).
- **Looks.** Looked at on a contact sheet: a scatter reveal of `pulse-circle` over a second (`ascii fx file --effect reveal --by scatter --at 0 --duration 1`, then `ascii render --sheet-frames 16`) shows a few cells at the first frames, then fills in steadily to the full circle by the tenth frame, and the last two frames are the untouched picture.

#### 5. Layers

A scene may have `layers` instead of one grid. Each layer is a small ASCII animation of its own with a position:

```json
"layers": [
  { "id": "water", "source": { "file": "water.gertie.json", "cols": 160 } },
  { "id": "koi", "framesFile": "koi.txt", "color": "#e5533c", "at": [[0, -30, 12], [6, 170, 40]], "fx": [] },
  { "id": "caption", "text": ["SCENE 01", "SUBJECT: KOI"], "at": [[0, 2, 2]], "color": "#cbd5e1", "fx": [ { "effect": "type", "at": 0.5 } ] }
]
```

- A layer has exactly one of `source`, `framesFile`, `frames`, or `text` (a still block of rows), plus optional `id`, `color`, `at`, `fx`, `from` and `to` (seconds it exists), and `loop` (default true: a layer shorter than the scene repeats).
- `at` is keyframes `[seconds, column, row]` of the layer's top-left cell in the scene grid, interpolated linearly and rounded to whole cells. One key, or none, is a fixed position (default 0, 0). Positions may be off the grid; cells outside are dropped. An optional fourth item is an easing name from the vector engine's list (`src/presets/easing.ts` is reused; `hold` steps).
- Layers are drawn in order, later on top. A space is transparent. A non-space cell replaces the cell under it, colour and background included.
- The scene's `cols` and `rows` are required with `layers` (`E-ASCII-SIZE`), and the scene's length is `duration` in seconds, also required.
- Flattening is a pure function `flatten(scene, t)` used by `framesOf`. Layer effects run before flattening; scene `fx` after.
- This is the route for anything built from scratch with several moving things: the agent draws or converts each sprite once and moves it with three numbers per keyframe, instead of redrawing whole frames.

**Decision.** No rotation or scaling of layers. A fish that turns is a sprite converted from a vector scene in which it turns. Rotating a character grid gives garbage.

**As built (task 5).** `src/ascii/layers.ts` (`flatten`, `positionAt`, `layerTimeline`, `layeredFrames`), the layer parser in `src/ascii/parse.ts` (`parseLayered`, `readKeys`), the `type` effect in `src/ascii/fx.ts`, and `framesOf`, `shapeOf` in `src/ascii/frames.ts`. `layers.ts` has no file or process access (the purity unit test now reads it too). Details the design does not say, and the decisions taken:

- **Fields and lint.** A layer has `id` (lowercase, digits, hyphens, unique), exactly one of `source`, `framesFile`, `frames` or `text`, and optional `color`, `at`, `fx`, `from`, `to`, `loop`. A new code, **`E-ASCII-LAYER`**, covers an unknown layer field (with the nearest name), a bad or repeated `id`, a bad `text`, bad keys, `from` and `to` (0 to the duration, `to` after `from`) and `loop`; none or two pictures is `E-ASCII-FRAMES`; a bad `color` is `E-ASCII-COLOR`. Problems inside a layer's `source`, `frames` and `fx` keep their own codes (`E-ASCII-SOURCE`, `E-ASCII-FRAME`, `E-ASCII-FX` and the rest), with the path moved under the layer (`layers[1].source.cols`) and the message starting with the layer's index and id (`layers[1] ("koi"): ...`). `layers` excludes `frames`, `framesFile` and `source` (`E-ASCII-FRAMES`). With `layers`, `cols` (up to 400), `rows` (up to 200) and `duration` (seconds, above 0) are required, `E-ASCII-SIZE`; `duration` times `fps` above 3600 frames is `E-ASCII-TOOMANY`; `duration` on a scene without layers is `E-ASCII-SIZE`. A layer's inline frames keep the inline limits (240 columns, 120 rows, 1200 frames); its grid is its widest row by its tallest frame. Paths in a layer are relative to the scene file, and a layer's `source` is read through the same injected `read` as a recipe.
- **`color`.** Fills the cells of the layer that have no colour of their own (frame `colors` win). The design's example said `"colors"` on the koi layer; the field is `color`, and the example is corrected.
- **Time.** Everything in a layer is in scene seconds: `at` keys, `from`, `to` and the layer's `fx`. **Decision:** a layer's own frames start at its `from` (so a layer that appears at 2 s starts its animation then), and its effects run on its timeline in scene time, before flattening, so an effect is not repeated each time a short layer loops. Times are rounded up to the next frame interval, as in part 4. Before `from` and from `to` on, the layer draws nothing. A `source` layer is converted as a recipe of its own at the scene's frame rate and cell shape, and again on each pass when it loops.
- **Positions.** `[seconds, column, row, ease?]`, keys in strictly increasing time. The easing is on the key a stretch starts from, as in the vector engine; absent means linear (not the vector engine's default `easeInOut`, because the design says "interpolated linearly"); a name from `src/presets/easing.ts`, a bezier `[x1, y1, x2, y2]` or `hold`. `bounce`, `elastic` and `spring` are refused. Positions round to whole cells (`Math.round`). Before the first key and after the last the layer stays at that key.
- **Flattening.** `flatten(layerFrames, positions, cols, rows)` (the design's `flatten(scene, t)` became this, because the frames of a layer at a moment come from a stream): layers in order, later on top; a space is transparent, also when it has a background; a non-space cell replaces the cell under it, its colour and background included, and a null colour or background replaces too (the style colour, no fill). `layeredFrames` steps every layer interval by interval and folds identical neighbouring results into one frame with a longer hold, so the holds add up to `duration * fps`. Then the scene's `fx` run on the result, as for the other forms.
- **`type`.** Typed cells are, row by row, every cell up to the last non-space cell of the row, so spaces inside a row are typed and row ends are not. At `at + n / cps` seconds, `n` cells have appeared, and the newest of them is drawn as `█` in its own colour; before `at` nothing is drawn; once every cell is typed the cursor goes and the text stays. Typing never changes a colour. Only a text layer can type (`E-ASCII-FX` elsewhere). `applyFx` applies it only when given `typing`, with the typing time as the entry's duration, which `layerFx` computes.
- **Renderer choice.** A scene with layers counts one frame per interval, the most there can be, as scene effects do: how many frames fold together is not known before flattening. So 60 by 24 cells at 10 fps for 4 s (96,000 cells) is SVG, and 180 by 50 at 24 fps for 8 s is the canvas renderer. `shapeOf` opens every layer's `source` (checking its crop and frame limit) without converting it, and `ascii lint` therefore reports source problems. A scene with layers has no frame-content warnings (blank, static, loop jump), like a recipe.
- **Command line.** `lint`, `render`, `play` and `export` handle layers through `shapeOf` and `framesOf`; their summary line reads "3 layers on 60 by 24 cells, 40 frames ...". There is no `ascii` subcommand for writing layers: the agent writes the `layers` list.
- **Looked at.** A 60 by 24 scene at 10 fps for 4 s with a starfield layer (the frames of `ascii gen stars --cols 60 --rows 24 --frames 20`), the rocket of `examples/ascii/rocket.txt` as a `framesFile` layer keyed from row 24 to row -14 with `easeIn`, and a typed caption of two rows: lint gives zero errors and the 16 frame sheet shows the stars throughout, the rocket entering from the bottom and leaving at the top, and the caption typing with the cursor and then staying. Stars show through the spaces inside the rocket's body, which is what the transparency rule says; a sprite that should read as solid needs cell backgrounds (`--cell-bg`) or characters in place of those spaces.
- **Fixed in task 6.** `layeredFrames` closed its layers only after the last frame, so a caller that stopped early (`ascii play --frame n`) left a `source` layer's converter, and for a vector scene its browser, open, and the process never exited. The layers are now closed in a `finally`; a unit test stops after two frames and checks that the source was closed (it fails without the fix). `ascii play --frame 5` on `letter-field.ascii.json` now takes 3.7 seconds.
- **Not done.** No rotation or scaling, as decided. A `framesFile` layer cannot name another `.ascii.json`: frames from `ascii gen` are copied into the layer's `frames`, or written to a text file.

#### 6. Reading a reference: `ascii probe`

`gertie ascii probe <clip|image> [--time s] --json` reports what the agent needs in order to imitate an ASCII reference: the cell pitch in source pixels and so `cols` and `rows`, the background colour, the five most common foreground colours, the frame rate, and a guess at whether cells are characters or dots.

- Cell pitch: take one frame as luma, sum along each axis to get a profile, and find the first strong peak of the profile's autocorrelation between 3 and 40 pixels. Report `null` when the peak is under 0.3 of the zero-lag value, which means the picture is not on a grid.
- Dots or characters: within cells, dots have the same shape scaled; report `"dot"` when the variance of the normalised cell images is under a threshold, else `"text"`.
- **Verify during build:** both rules, on frames made by Gertie itself at known grid sizes (40, 120 and 200 columns, text and dot), and say in this document how often they are right. If the pitch cannot be found reliably on compressed video, keep the command but report colours and frame rate only, and tell the agent to count cells on an enlarged crop from `gertie grid`.

It does not read which characters are used; the agent reads those from an enlarged crop.

**As built (task 6).** `src/ascii/probe.ts` (pure: `probeFrame`, `profilePeriod`, `backgroundOf`, `changeRate`) and `ascii probe` in `src/cli/lib/ascii-command.ts`, which takes one frame with ffmpeg at full size and up to 3 seconds of small frames for the change rate. Unit tests on synthetic rasters are in `tests/unit/ascii-probe.test.ts`. The rules as built, and how they differ from the design:

- **Background.** The colour of the outermost ring of pixels when at least 60 percent of the ring is that colour, else the most common colour (buckets of 8 levels per channel). The design's "most common colour" was wrong for large dots, which can cover most of the frame (a synthetic test of dots up to 95 percent of the cell). A gradient is reported (`from`, `to`, `angle` 180 or 90) when the top and bottom strips, or the left and right ones, differ by more than 24, and ink is then measured against the gradient, not one colour.
- **Ink.** A pixel is ink when its colour is more than 48 (of 441) from the background. The profiles are column and row sums of ink, so coloured glyphs on a coloured background count, not only luma.
- **Pitch. Change from the design:** the autocorrelation peak was tried first and failed in two ways. On a frame with one large shape the profile is a broad bump, every lag correlates, and the refinement walked down to a pitch under one pixel (every 120 and 200 column clip of `rocket-launch`). With the profile high-passed (less its moving average) it was right on 11 of 12 `rocket-launch` clips but found no peak on one axis of the twelfth, and on sparse frames it found nothing or a wrong period. As built, the period is the strongest **Fourier component** of the high-passed profile (the magnitude at that period over the sum of absolute values, 0 to 1), scanned from 3 to 80 pixels in steps fine enough that the phase cannot slip a quarter period across the picture, then refined with a parabola. Three further rules came from failures: thin strokes put energy in harmonics, so the cell is the largest whole multiple of the strongest period that keeps at least 0.35 of its strength, is 1.5 times stronger than the periods half a step either side (a sharp peak, not the broad rise of a large shape) and leaves six periods in the ink; the range was raised from 40 to 80 pixels because a 40 column clip scaled to 1080 pixels has 54 pixel rows; and periods up to 40 are read from a profile high-passed over 83 pixels, larger ones over 163, because the wider filter alone left a small object's own bump in the profile and weakened its cells to under the threshold. No grid (`pitch: null`) when either axis is under 0.3, or the ink spans under six periods, or **fewer than 40 cells have ink**. That last rule was added because the middle frame of `night-sky` (about eight stars) gave confident wrong pitches of 22 to 39 pixels. `cols` is `floor(width / pitch + 0.25)`, so Gertie's padding of half a font size counts as about one more column: 40 columns read as 40 or 41.
- **Dots or characters. Change from the design:** the measure is not the variance of normalised cell images but the mean **mirror asymmetry** of the inked cells, left-right and top-bottom about each cell's ink centroid, measured against the cell's own corner colour (so a cell background is not taken for a symmetric dot). It is `dot` under 0.15. Measured: at cells of 8.9 pixels or more, dots 0.00 to 0.06 and characters 0.27 to 0.35, with no overlap; at 5 and 6 pixel cells, dots 0.04 to 0.39 and characters 0.22 to 0.30, which overlap. So the glyph is reported only when the smaller side of the cell is at least 8 pixels, and is `null` with a note below that.
- **Colours.** The strongest ink pixel of each inked cell, so antialiased edges and glow do not count, in buckets merged when closer than 48, the five largest with their shares. On the bouquet example's MP4 they are `#db8fa8` 44 percent, `#6a9458` 37 and `#ededed` 19: its palette of pink, green and white.
- **Additions.** The frame defaults to the middle of a clip (a reveal or typing has usually finished by then), `--time` picks another. Besides `fps` from the container it reports `changesPerSecond`: of the steps between frames at the clip's own rate over up to 3 seconds, those where more than 0.05 percent of pixels (and at least 3) change, per second. A `note` says why the grid or the glyph is null and what to do instead: probe another frame with `--time`, or count cells on an enlarged crop with `gertie grid`.

**Verify during build: done.** Clips made by Gertie from four vector scenes (`rocket-launch`, `gradient-orb`, `candle`, `night-sky`), converted at 40, 120 and 200 columns as text (`long` ramp, colour) and as dots (square cells), at font sizes 16, 10 and 8, and exported to MP4 and GIF: 48 clips at scale 1 (cells 5 to 10 pixels wide), 24 more at `--scale 2` (cells 10 to 12 pixels), and 8 re-encoded with ffmpeg to 1080 pixels wide at CRF 32 and 720 pixels at CRF 28, which gives cells of fractional size (3.57 to 26.35 pixels) and heavy compression. Results, 80 clips:

| | Clips | Columns within 5 percent | Wrong | No grid reported |
|---|---|---|---|---|
| Frames full enough to read (`rocket-launch`, `gradient-orb`, `candle`) | 68 | 68 | 0 | 0 |
| Sparse frames (`night-sky`: about eight stars in the middle frame) | 12 | 0 | 0 | 12 |

The glyph was right in all 39 clips where it was reported (cells of 8 pixels or more), and `null` in the 29 others with cells under 8 pixels. Pictures with no character grid (two images and two contact sheets of vector scenes) gave no grid; a third contact sheet gave an 8 pixel grid, which is correct: its frame labels are monospaced text. The pitch held on compressed video, including at fractional cell sizes, so the fallback the design named (colours and frame rate only) was not needed; the command still reports `null` rather than a guess when the evidence is weak. **Not verified:** clips made by other tools (other fonts, other cell spacing, motion blur or scaling filters), and the owner's reference clips, which are not in the repository. Every case above was a Gertie export.

### What the agent does, after this phase

`skills/gertie/references/ascii.md` gets two playbooks in place of the four routes:

- **From scratch.** Small and simple: write frames, as now. Anything with smooth motion, many parts or more than about 60 columns: build it as a vector scene with bold shapes and flat colours, pass `qa`, then make a recipe with `ascii from scene --recipe --cols 120 to 200`, a palette, and one reveal. Several things moving independently: layers. Never draw a large picture in characters by hand.
- **From a reference.** A picture or video to turn into ASCII: `ascii from` with `--key auto`, `--normalize`, then choose the look (ramp, `--chars`, dots) and one effect. An ASCII clip to imitate: `ascii probe` for the grid and colours, an enlarged crop for the character set, `study` for the timing, then build the same structure with original art. The rights rules in `10-references.md` apply.

It also gets a table of looks, each a ready combination: "CRT bouquet" (`long` ramp, palette, glow), "halftone" (`glyph` dot, `cellAspect` 1, colour), "letter field" (`--chars`, colour, shimmer), "bands" (`bands` ramp, edge colour), "solid sprites" (colour with `--cell-bg`).

**As built (task 6).** `skills/gertie/references/ascii.md` is rewritten around the two playbooks, with a table of five looks, each one an example in `examples/ascii/` with the exact command or fields that make it: the CRT bouquet, the halftone, the letter field, bands, and a layered pond (which replaces "solid sprites" as a row; `--cell-bg` is described under the table). Every command line in it was run verbatim, in a copy of the skill folder with the example files beside it: 14 commands, all exit 0. Findings while making the examples:

- **A still picture has no time.** A recipe of an image is one frame long (0.04 s at 24 fps), so an effect cannot run on it (`E-ASCII-FX`, the range is outside the animation). The halftone puts the picture in a `source` layer of a scene with a `duration`, and gives the scene the reveal. The reference text says so.
- **`--gamma` matters for bands.** With a vector scene on black, most of a lit sphere is far from the background, so the brightest band covered half of it; `"gamma": 1.8` and a tighter gradient in the scene gave four bands of useful size.
- **A GIF note is misleading.** Exporting a GIF without `--bg` prints "Transparent GIF has one bit of transparency..." even when `style.background` is a solid colour; the bouquet's GIF has no transparent pixel. The condition in `src/export/index.ts` checks only the `--bg` flag, not the scene's background. Not changed in this task (it is shared with vector export); the reference text tells the agent the note can be ignored with a solid background.
- **The examples' sources live in `examples/ascii/`** (`bouquet.gertie.json`, `sunflower.gertie.json` and the `sunflower.png` rendered from it at 0 s, `star-flower.gertie.json`, `orb.gertie.json`, `water.gertie.json`, and the sprites `koi-right.txt`, `koi-left.txt`, `lily.txt`), not in `examples/`, so they are not part of the vector golden corpus. Each passes `qa` with 0 errors and 0 warnings. A scrolling `x` with `repeat: "loop"` warns `W-LOOP-JUMP` even when the step is one wave period, so the water slides with `pingpong` instead.

### Left out

- **Glyph matching by shape** (choosing the character whose strokes best fit the cell's edges). Better outlines at low density; at the densities here brightness is enough.
- **Outlined glyphs in SVG** (`--outline`), still a later version.
- **3D sources.** The turning flower is a 3D render converted to characters. Gertie converts whatever video it is given, and makes turning from 2D scenes by scaling a shape's width.
- **Sound.** The pond clip is driven by music. `story` already adds a track to a video.
